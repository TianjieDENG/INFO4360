Everyday Git Workflow

The commit-and-push cycle you'll repeat every time you work on the project, from Phase 1 through Phase 3. Bookmark this page.

Haven't created your repo yet? Start with GitHub Setup for the Group Project first. This guide picks up after your repo is created, cloned, and you've made your first commit.

Quick Reference: A Typical Session

Once you've done this a few times, here's the whole cycle in one place — including pulling your teammate's latest changes before you start, which the detailed steps below don't cover on their own.

git pull origin main    # start here: get your teammate's latest changes
git diff ORIG_HEAD HEAD  # check what changed while you were away

# ...make your edits, save files...

git status               # see what changed
git add .                # stage it
git commit -m "..."      # commit with a clear message
git push origin main     # send it to GitHub

In VS Code: click Sync Changes when you open the project (pulls), check what changed, do your work, then stage your changes, write a message, commit, and click Sync Changes again (pushes). The step-by-step version below walks through each piece in more detail.

The Cycle

Every time you sit down to work, do these three things first, in this order:

  1. Pull your teammate's changes (click Sync Changes, or run git pull origin main).
  2. Check what changed since you last worked. See the section on checking changes below.
  3. Make your changes. Only now start editing.

Then move through the five steps below. Skipping the check is how two people end up quietly undoing each other's work.

How often should you commit? Whenever you finish a logical unit of work — added a new analysis, fixed a bug, wrote a new section — not just once at the end of a long session. Smaller, frequent commits are easier to describe accurately, easier to undo if something breaks, and build the commit history the project rubric actually looks for.

Step 1: Make Your Changes

Edit your notebook, scripts, README, whatever you're working on. Save as you go (Ctrl+S or ⌘S). Nothing leaves your computer yet — this is all local.

Step 2: Check What Changed

Open the Source Control panel in VS Code (branching icon in the left sidebar, or Ctrl+Shift+G / ⌘⇧G). You'll see every file you've touched listed under Changes.

Prefer the command line?

git status

Red or modified files are changes not yet staged. This is a good habit before every commit — it's easy to forget you edited a file three tabs ago.

Step 3: Stage Your Changes

In Source Control, click the + next to a file to stage it, or the + next to "Changes" to stage everything at once.

Prefer the command line?

git add .

The . means "everything that changed." If you only want to stage one file, use git add filename.ipynb instead.

Step 4: Commit With a Message

Type a message in the box at the top of Source Control, then click the checkmark (or Ctrl+Enter with your cursor in the box).

Prefer the command line?

git commit -m "Add keyword frequency analysis"

Step 5: Push to GitHub

Click Sync Changes (or the up-arrow icon) in Source Control.

Prefer the command line?

git push origin main

If this is rejected, see Working With a Teammate below.

Checking What Changed

Check at two moments: after you pull (what did my teammate do?) and before you commit (what am I about to save?). A diff is the line-by-line view of those changes.

In VS Code

  1. Open the Source Control panel (Ctrl+Shift+G / ⌘⇧G).
  2. Click any file under Changes. A side-by-side view opens: removed lines on the left, added lines on the right.
  3. To see what a teammate pushed: open the Source Control Graph, click their commit, then click a file in the list that appears.

On the command line

git diff                    # your edits, not yet staged
git diff --staged           # what's staged for the next commit
git diff ORIG_HEAD HEAD     # everything the last pull brought in
git log --oneline -5        # the five most recent commits
git show <commit-hash>     # one commit's full changes

In a diff, a line starting with + was added and a line starting with - was removed. Press q to leave the diff view in the terminal. ORIG_HEAD points to where you were before your last pull, so the pull diff only makes sense right after pulling.

Working With a Teammate

If you're on a team, you'll sometimes try to push after your teammate already pushed their own changes. Git will refuse rather than silently overwrite anything.

  1. In VS Code, click Sync Changes again — it will pull your teammate's commits, merge them with yours automatically, and then push.
  2. On the command line, run git pull origin main first, then git push origin main.

This usually resolves on its own. If VS Code reports a merge conflict (the same lines changed in two different ways), it will mark the conflicting section in the file — resolve it by editing the file to keep the version you want, then repeat Steps 3 through 5 above.

Tip: pull before you start working, not just when a push fails. Running git pull origin main (or clicking Sync Changes) at the start of a session means you're always building on your teammate's latest work instead of finding out later. If VS Code asks whether it can periodically run git fetch, say yes — it's safe (it only checks GitHub for updates, it never changes your files) and it makes it obvious the moment your teammate has pushed something new.

If You Don't Like a Teammate's Change

Talk to them first. They may have a reason you can't see from the diff, and the fix is often a quick conversation rather than a rewrite.

If you still want it undone, use revert. It creates a new commit that reverses the old one, so the history stays intact and your teammate can see what happened.

The simplest route is the command line in VS Code's terminal (Terminal → New Terminal), then click Sync Changes so the revert reaches GitHub.

Run:

git revert <commit-hash>
git push origin main
Avoid git reset --hard. It throws away local commits and uncommitted edits, and on a shared repo it can erase your teammate's work from your copy. Use revert instead.

Reverting to an Earlier Version

There are three common cases.

  • Undo one whole commit: git revert <commit-hash>, as above.
  • Bring back one file as it was in an earlier commit: git restore --source <commit-hash> -- filename.ipynb. Then stage and commit the file like any other change.
  • Look at an old version without changing anything: git show <commit-hash>:filename.ipynb.

To find a hash, run git log --oneline, or open the repo on GitHub.com and click the commit count. Copy the first 7 characters; Git accepts the short form.

Other Common Situations

Not errors — just things you'll want to do often.

See what changed, before you commit

See Checking What Changed above for diffs in VS Code and on the command line.

See your commit history

On GitHub.com, open your repo and click the commit count (or the clock icon) near the top of the file list. In VS Code, open the Source Control Graph panel (or the "..." menu in Source Control → View History).

Prefer the command line?

git log --oneline

See what a specific past commit changed

On GitHub.com, click into any commit from the history list to see its diff. In VS Code, find the commit in the history/graph view and click it.

Prefer the command line?

git show <commit-hash>

Grab the hash from git log --oneline — you only need the first 7 characters or so.

Undo changes you haven't committed yet

Made a mess and want to throw it away? In VS Code, right-click the file in Source Control and choose Discard Changes. This reverts the file to how it looked at your last commit — it cannot be undone, so use it only on changes you're sure you don't want.

Prefer the command line?

git restore filename.ipynb

Common Issues

"Sync Changes" is grayed out

Nothing is staged or committed yet. Complete Steps 3 and 4 first.

"Push rejected" or "Your branch has diverged"

Your teammate pushed first. See Working With a Teammate above.

"Everything up-to-date" but your changes aren't on GitHub

Your changes were never staged or committed — only pushed commits show up remotely. Run git status to check, then repeat Steps 3 and 4.

Asked to sign in to GitHub

Normal the first time on a new machine. Follow the browser window that opens and authorize VS Code.

Merge conflict markers in a file (<<<<<<<, =======, >>>>>>>)

Git couldn't automatically combine two changes to the same lines. Edit the file by hand to keep the version you want, delete the marker lines, save, then stage and commit as usual.
